# Bundled dependency provenance

This page records the old third-party code that is visibly embedded in the
original ARM64 `libqplay.so`. It matters for two reasons. First, the Android
system cannot update these implementations independently because the library
does not depend on system zlib, bzip2, or FreeType. Second, several of the
entrypoints are reachable from protocol or resource data.

The detailed IDA export is
`artifacts/original_dependency_provenance_20260830.json`. It was generated by
`tools/ida_export_original_dependency_provenance.py` from the original ARM64
IDB. The export is read-only, contacts no server, and contains no fuzzing
results.

## Version inventory

| Component | Version evidence | Important entrypoints | Input boundary |
| --- | --- | --- | --- |
| zlib | `zlibVersion` at `0x289b50` returns `1.2.5` | `uncompress`, `inflate`, `inflateInit_`, `inflateInit2_` | NewGraal and legacy protocol compression, PNG/MNG, and ZIP entries |
| bzip2 | `BZ2_bzlibVersion` at `0x2751ac` returns `1.0.4, 20-Dec-2006` | `BZ2_bzBuffToBuffDecompress` | NewGraal selector 2 and legacy modes 5 and 6 |
| FreeType | `FT_Init_FreeType` at `0x253f1c` writes library fields `2`, `3`, and `6` | `FT_New_Face`, `FT_New_Memory_Face` | System font paths and resource-backed font streams |
| libjpeg | Exact release not recovered | `jpeg_std_error`, `jpeg_CreateDecompress` | Extension-selected downloaded image resources |

The version conclusions are based on code behavior, not only on nearby
strings. zlib and bzip2 expose version functions that return the recovered
release text. FreeType initialization writes the three version fields into the
new library object. The libjpeg ABI constants are deliberately not treated as
a release identifier.

`readelf -d` lists only `libGLESv1_CM.so`, `libc.so`, `libstdc++.so`, `libm.so`,
and `liblog.so` as needed libraries. There is no `libz.so`, `libbz2.so`, or
`libfreetype.so` dependency. The versions above are therefore properties of
the native binary itself.

## Reachability

The protocol parser selects two compression wrappers. In the legacy parser at
`0x1fc598`, modes 3 and 4 call
`TCompression_DecompressBuf_void_const_int_uchar_uint` at `0x1fc680`, while
modes 5 and 6 call
`TCompression_DecompressBuf2_void_const_int_uchar_uint` at `0x1fc8a4`. The
first wrapper uses zlib and the second uses bzip2. The NewGraal parser at
`0x1fe31c` uses the same wrappers for selectors 1 and 2 at `0x1fe880` and
`0x1fe868`.

The automatic wrapper path uses a shared native output buffer. It starts at
least 64 KiB, retries after an output-buffer-full result, and accepts growth
through 4 MiB. `TCompression_getCompressionBuffer_int` rounds requested sizes
to powers of two and has no independent upper bound. The 4 MiB behavior is a
per-call output policy, not a complete limit on the input stream or the total
resource set.

zlib has two additional resource consumers. The PNG/MNG parser at `0x11f9d8`
calls `inflate` and `uncompress`, while the ZIP reader at `0x24b174` calls
`inflate` for deflated entries. The image review already found that PNG IDAT
data and decoded image dimensions lack a common application budget.

The font loader at `0x110ca0` first checks the configured font path. It can
load a system font with `FT_New_Face`, or pass a resource stream to
`FT_New_Memory_Face`. If a relative resource is missing locally, the loader
asks the file-download and resource layer for it. This makes the memory-face
path a conditional downloaded-input boundary, although the stock flow has not
been shown to let an untrusted caller choose arbitrary font data.

JPEG is included to keep the inventory honest. `TBitmap_readJPEG_TStream` at
`0x150fa8` reaches the bundled decoder, but the exact libjpeg release was not
identified and no new JPEG vulnerability claim is made here.

## Security interpretation

Three conservative findings are recorded in the machine-readable export:

* `DEP-001` is an old-dependency exposure. zlib 1.2.5 and bzip2 1.0.4 are
  statically present on accepted protocol and resource paths. The exact
  source revisions and vendor backports have not been reconstructed, so this
  is not a claim that a specific CVE is exploitable in this APK.
* `DEP-002` covers resource-backed font data reaching FreeType 2.3.6. Native
  font parsing deserves its own input and allocation budget, but arbitrary
  server control over the font option has not been established.
* `DEP-003` covers the shared decompression buffer. Automatic output growth is
  limited in one wrapper, but compressed input accumulation and broader native
  resource budgets remain separate concerns.

The upstream [zlib 1.2.x ChangeLog](https://raw.githubusercontent.com/madler/zlib/v1.2.12/ChangeLog)
records later inflate validation and other parser fixes. That history is useful
for deciding what source diff or fuzzing to perform, but it does not prove that
the vendor made no backports. The [bzip2 historical source archive](https://www.sourceware.org/pub/bzip2/)
provides the matching 1.0.4 source package for a future code comparison.

## Follow-up work

The highest-value next step is a disposable local harness that exercises the
protocol compression selectors, PNG or ZIP decompression, and font loading.
The harness should impose compressed-byte, decoded-byte, image-dimension,
font-byte, and total-allocation budgets, and should preserve the original
binary as the comparison target. A source-level repair should then update the
bundled libraries or prove the required vendor backports before the old client
is used against untrusted services.
